01
Why It Matters

Почему результат теста — ещё не вся картина?

Представь, что разработчик правильно написал GET /products/_doc/42. Это говорит о знании REST API, но пока не доказывает, что он способен диагностировать ошибку в production, учитывать права или подготовить проверяемые тестовые данные.

Observation

Что произошло?

Собираем факты: входные данные, версию, ожидаемый и фактический результат.

Gap

Чего не хватает?

Пробел в знаниях, проверке, объяснении или воспроизводимости — это разные вещи.

Action

Что делать дальше?

Назначаем конкретную задачу и способ повторной проверки, а не общее «почитать больше».

Что научишься делать: отличать факт от предположения, классифицировать пробелы, составлять карту Mastery 0–5, диагностировать задержки данных и создавать измеримый план на следующие уроки.

Что нужно знать заранее: основы HTTP, JSON, Docker и разницу между Expected и Actual Result (M00-L01–L03). Здесь используется вымышленный магазин AcademyShop с синтетическими данными.

От ошибки к плану: пять понятных шагов

→

→

Evidence (доказательство) — сведения, по которым другой инженер может повторить эксперимент. Gap (пробел) — конкретное умение, ещё не подтверждённое проверкой. Mastery — уровень владения навыком, а не процент правильных ответов.

Четыре разных статуса

Published — материал существует. Studied — его изучили. Submitted — работа сдана. Verified — наставник проверил результаты по критериям и сохранил Evidence.

Уровни Mastery

0 — нет подтверждения; 1 — узнаю термин; 2 — объясняю; 3 — самостоятельно применяю; 4 — диагностирую; 5 — проектирую и обучаю других.

Важное различие: знание синтаксиса API может быть Verified на уровне 3, а умение расследовать задержку данных пока оставаться на уровне 2. Это не противоречие: проверяются разные компетенции.

03
Guided Worked Example · Не оценивается

Разбор одной ошибки — с начала до конца

Сценарий для тренировки: в тестовом API пользователь пытается прочитать отсутствующий товар с ID 999.

Входные данные
GET /api/products/999
Seed: только товары 1 и 2
Expected: 404 Not Found
Actual: 404 Not Found

Тест проходит: сервер правильно сообщает, что товара нет.

Инженерная интерпретация

PASS подтверждает обработку отсутствующего ресурса, но не доказывает, что API возвращает правильный товар для существующего ID.

Gap: не хватает теста успешного получения существующего товара. Action: добавить отдельный сценарий с известным ID и ожидаемыми полями.

Полный вывод: мы знаем вход, предварительные данные, Expected, Actual и границы доказательства. Решение — не «переписать HTTP», а добавить недостающий тест. Этот пример разобран полностью и не является ответом на самостоятельную лабораторную ниже.

06
Interactive 03 · Data Flow

Как цена проходит из PostgreSQL в поиск?

Представь магазин, в котором цена товара меняется с 100 на 120. Elasticsearch используется как поисковая проекция. Обновление может проходить через фоновый worker (обработчик сообщений), а после индексирования поиск может ждать refresh — момента, когда новые данные станут доступны для поисковых запросов.

Почему Elasticsearch иногда возвращает старые данные, даже если документ уже записан?

Near real-time search (поиск почти в реальном времени) означает, что недавно записанные документы могут становиться видимыми для поиска после refresh. При этом GET /{index}/_doc/{id} имеет собственную семантику чтения и может увидеть документ раньше поисковой выдачи. Не путай задержку доставки данных в Elasticsearch с задержкой refresh уже проиндексированного документа.

Подробнее: официальная Near real-time search и Refresh parameter.

Technical Deep Dive · Маленькими шагами

Пять типов пробелов и как их закрывать

Knowledge

Не знаю понятие

Учебная задача: объяснить термин и привести свой пример без подсказки.

Correctness

Неверный результат

Сравнить Expected и Actual на данных, которые способны выявить ошибку.

Evidence

Нельзя воспроизвести

Добавить seed, сборку, точные шаги, статус, фактический ответ и дату.

Diagnostics

Не найдена причина

Сформулировать гипотезы и эксперимент, который различит эти гипотезы.

Safety

Риск для production

Проверить права, изоляцию среды, отсутствие секретов и безопасное действие.

Planning

Нет следующего шага

Назначить действие, критерий успеха и дату повторной проверки.

Воспроизводимая диагностика — как мыслит инженер

REST · read only
GET /products/_doc/42

GET /products/_search
{
  "query": {
    "ids": { "values": ["42"] }
  }
}

Эти примеры читают данные разными механизмами. Для выполнения в реальности предварительно убедись, что индекс и документ существуют и есть права read.

ASP.NET Core · модель
// Для диагностики логируй метаданные:
// correlationId, documentId,
// expected, observed, version,
// timestamp и outcome.
// Не логируй credentials и PII.

В TypeScript/Next.js браузер отправляет запрос твоему серверу, а не обращается к закрытому Elasticsearch с API-ключом. Весь анализ проводится на безопасных тестовых данных.

Не используй Refresh API как «волшебную кнопку исправления». Он влияет на видимость уже проиндексированных документов, но не доставляет потерянное сообщение из очереди и не исправляет неверно выбранный индекс. Частые принудительные refresh могут ухудшить производительность. Сначала диагностика, потом вмешательство.

Когда ставить повторение?

Spaced repetition (интервальное повторение) — возвращение к задаче через время, чтобы подтвердить долговременное понимание. Для Academy используем ориентиры 1, 7, 21 и 60 дней. Повторная проверка должна быть новой самостоятельной попыткой, а не копированием старого ответа.

Сценарий AcademyShop · Синтетические данные

Два наблюдения из тестовой среды

Инцидент A: цена товара id=51 в PostgreSQL обновилась до 220 в 14:00. В 14:03 API поиска всё ещё возвращает 180. Лог worker за этот период не приложен. Известна лишь версия Elasticsearch Stack 9.x.

Инцидент B: коллега ожидает HTTP 200 на GET /products/_doc/42, но получает 403. Для теста не записано, какими правами обладал токен. Seed содержит товар 42, а источник API Reference указан без даты проверки.

Данные вымышленные; не нужно запускать реальные запросы. Твоя цель — не угадать одну причину, а предложить способ различить возможные причины.

Часть A · Evidence

От факта к гипотезам

Для каждого инцидента раздели подтверждённые факты и предположения. Запиши минимум две возможные причины и конкретную проверку, которая помогла бы их различить.

Часть B · Plan

Приоритеты и ограничения

Определи порядок безопасных действий: что проверить первым, что вторым, что не следует делать сразу. Укажи права доступа, предусловия и критерии успешной диагностики.

Часть C · Growth

Карта навыков

Выбери 3–5 умений, которые уже можешь подтвердить своими работами, и 1–2 навыка для углубления. Для каждого укажи уровень 0–5 и чем его докажешь.

Часть D · Evidence / Handoff

Передача работы

Подготовь воспроизводимый отчёт: источники, дата, версии, ожидаемые/фактические наблюдения и план повторений. Отдельно укажи, что именно остаётся неизвестным.
