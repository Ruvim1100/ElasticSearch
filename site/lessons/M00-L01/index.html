02 · Зачем это нужно

Почему одного «вроде работает» недостаточно

Представь, что ты проверяешь поиск товаров для интернет-магазина на Next.js. Владелец магазина ожидает одно поведение, а программа иногда делает другое. Чтобы разобраться, мы записываем вход → ожидание → факт → вывод.

В

Вход

Что мы передали программе? Например, поисковую строку и номер версии.

О

Ожидание

Как программа должна ответить по требованию заказчика?

Ф

Факт

Как программа ответила на самом деле? Если не совпало — фиксируем ошибку.

Такую запись называют evidence (свидетельство, доказательство проверки). Хорошее evidence позволяет коллеге повторить опыт и получить тот же результат. Это основа качественного Code Review (проверки работы).

03 · Показываю полностью

Готовый пример, который не нужно сдавать

Сначала пример из обычного магазина, не из лабораторной работы. Требование: итоговая стоимость корзины равна цене одного товара 100 + двух товаров по 50. Значит, мы заранее ожидаем 200.

  1. Вход: один товар за 100 и два по 50.
  2. Ожидаемый результат: 200. Мы вычислили его по правилу до проверки.
  3. Фактический результат: выбери, что вернула программа, и нажми «Сравнить».
Нажми «Сравнить с ожиданием».
Что писать в отчёте после такой проверки?

Пример: «Правило — 100 + 2 × 50; ожидаю 200; программа вернула 210; проверка не пройдена. Повторить: задать те же цены и количество». Если фактический результат 200 — проверка пройдена. Записывать только «не работает» недостаточно.

Это весь принцип практики. В самостоятельном задании вместо стоимости корзины проверим поиск по названию товара. Мы не будем использовать настоящую базу данных или Elasticsearch: сначала разберёмся с методом проверки.

04 · Разбираемся с поиском

Три товара и два варианта поиска

Нам дан крошечный каталог. Каждая строка — товар. ID — короткий уникальный номер товара; название — то, по чему будем искать.

ID     Название
P1     Чай
P2     чай
P3     Кофе

Регистр букв — это разница между заглавной и строчной буквой: «Ч» и «ч». Пользователь может искать «Чай» или «чай», но заказчик хочет находить все подходящие товары независимо от регистра.

v1 — сравнение с учётом регистра

Программа сравнивает буквы буквально. Для неё «Чай» и «чай» — разные строки.

Это учебная версия поиска, не Elasticsearch.

v2 — сравнение без учёта регистра

Перед сравнением обе строки приводятся к одному регистру. «Чай» и «чай» становятся одинаковыми для сравнения.

Это тоже локальный учебный симулятор.

Требование заказчика: если название товара совпадает с запросом без учёта регистра, товар должен быть найден. Если совпадений нет — список пуст. Порядок найденных ID не важен.

Что означают слова «сборка», «запрос» и «найденные ID»?

Сборка (build) — версия программы: здесь v1 или v2. Запрос (query) — слово, которое вводит покупатель. Найденные ID (hits) — номера товаров, которые программа вернула. Знак ∅ означает пустой список, то есть «ничего не найдено».

05 · Тренируемся самостоятельно

Тренажёр поиска: сначала предположение, затем проверка

Здесь нет скрытых ответов: сначала ты сам указываешь, что должен найти поиск по требованию заказчика, а затем нажимаешь «Запустить». Страница покажет фактический результат выбранной версии и сравнит его с твоим ожиданием.

  1. Выбери версию программы (v1 или v2).
  2. Выбери запрос — слово покупателя.
  3. До запуска введи ожидаемые ID по требованию заказчика: например, P1, P3. Если ожидаешь пустой ответ, напиши нет. Это лишь пример формата записи, не правильный ответ для каталога.
  4. Нажми «Запустить проверку»; затем посмотри, прошла ли она.
Выбери сборку и запрос, запиши своё ожидание, затем запусти проверку.

Мой журнал наблюдений

Что делать, если ожидание и факт отличаются?

Это полезное наблюдение, а не ошибка твоей работы. Сопоставь результат с требованием заказчика: какая сборка отклонилась от требования и почему? Не исправляй ожидаемый результат только ради зелёной отметки: иначе тест потеряет смысл.

06 · Самостоятельная практика

Задание: какую версию поиска можно принять?

Теперь ты — разработчик, принимающий поиск для Next.js-витрины. Задача не в том, чтобы написать код. Нужно проверить две версии, записать результаты и обосновать решение. Всё можно сделать в тренажёре выше.

Условие: поиск должен находить все товары с названием, совпадающим с запросом без учёта регистра. Используй только товары P1, P2, P3, перечисленные выше.

  1. Выбери два запроса. Один должен иметь хотя бы одно совпадение в каталоге, второй — не иметь совпадений. Коротко запиши, почему выбрал именно их.
  2. Запиши ожидания заранее. Для каждого запроса определи ID, которые должны вернуться по условию задачи — независимо от того, как работает конкретная сборка.
  3. Проведи четыре проверки. Запусти оба запроса на v1 и на v2. В результате должно получиться ровно четыре основных наблюдения. Дополнительные эксперименты разрешены.
  4. Сделай вывод. Какую сборку ты бы принял для заказчика? Приведи хотя бы один конкретный результат, на котором основано решение.
  5. Объясни воспроизводимость. Что должен знать коллега, чтобы повторить твои проверки с нуля? Где хранится исходный урок, а где сохраняется подтверждённая оценка?

Образец структуры отчёта (ответы заполняешь ты)

Выбранные запросы: ... и ...

Как будет оцениваться практика

КритерийБаллыЧто проверит наставник
Данные и шаги20Можно повторить проверку
Ожидания20Основаны на требовании, а не на факте
Четыре наблюдения30Версия, запрос, ожидаемый и фактический ответ
Обоснованный вывод20Указаны доказательства выбора
Передача на ревью10Есть объяснение и контекст

Для зачёта практики требуется 90 из 100. Готовое решение мы не показываем до твоей самостоятельной попытки — зато есть весь необходимый материал и тренажёр.

07 · Проверяем понимание

Пять коротких вопросов

Ответь своими словами, по 1–3 предложения. Они нужны не для скорости, а чтобы убедиться, что логика понятна. Каждый вопрос — 20 баллов; порог теории — 80 из 100.

  1. Где лежит исходный HTML-код урока, а где хранится последняя подтверждённая оценка?
    Подсказка

    Вспомни три карточки в начале: исходники, сайт для чтения и таблица прогресса.

  2. Если урок появился на сайте, означает ли это, что ученик уже освоил тему?
    Подсказка

    Сравни Published и Verified.

  3. Теория оценена на 95/100, практика — на 89/100. Можно ли переходить дальше?
    Подсказка

    Посмотри два независимых порога выше.

  4. Два разработчика получили разные результаты одного запроса. Какие параметры эксперимента нужно сравнить прежде всего?
    Подсказка

    Посмотри на поля в журнале тренажёра.

  5. Что необходимо, кроме хороших оценок, чтобы урок получил статус Verified?
    Подсказка

    Вспомни самостоятельное объяснение, Code Review и запись в Tracker.

08 · Как закончить урок

Куда отправлять работу

  1. Закончи четыре проверки в тренажёре и скопируй журнал.
  2. Напиши короткий вывод и шаги воспроизведения по шаблону из задания.
  3. Ответь на пять вопросов из Knowledge Check.
  4. Отправь всё в чат с наставником. Я проведу Code Review, отмечу ошибки и попрошу исправления при необходимости.
  5. Только после успешной проверки и подтверждённой записи в Google Sheets урок станет Verified.

Личный чек-лист перед отправкой

Отмечено: 0 из 4. Это подсказка для подготовки отчёта, не оценка.

Чего страница НЕ делает: она не отправляет ответы наставнику, не записывает баллы в Google Sheets и не может присвоить Verified. Даже если все галочки отмечены, окончательное решение принимает наставник после проверки.

Словарь урока: ID, query, build, evidence, Code Review
ID
Уникальный идентификатор товара; здесь P1, P2, P3.
Query (запрос)
Текст, который покупатель вводит в поиск.
Build (сборка)
Отдельная версия программы; здесь v1 и v2.
Expected / Actual
Ожидаемый результат по требованию / фактический результат программы.
Evidence
Данные проверки, по которым другой инженер может её повторить.
Code Review
Проверка правильности и качества выполненной работы.
Verified
Компетенция проверена наставником и подтверждена в Tracker.
