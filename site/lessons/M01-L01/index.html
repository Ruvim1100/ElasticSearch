Цель

Что должен уметь разработчик после урока

Объяснить своими словами почему полнотекстовый поиск отличается от SQL-фильтрации, разделить ответственность PostgreSQL и Elasticsearch в реальном приложении и описать путь записи/чтения.

Объяснить

Document, index, inverted index, search relevance.

Спроектировать

Где находится source of truth, где поисковая проекция.

Предотвратить ошибку

Не заменить транзакционную БД поисковым движком без необходимости.

Ключевой принцип: Elasticsearch — распределённый поисковый и аналитический движок. PostgreSQL — реляционная транзакционная СУБД. Это не «кто быстрее», а какую задачу решаем.
Модель

Одна задача — две роли

Представь каталог из 1 млн товаров. Приложению нужны обновление цены и остатков, транзакции покупки, а также поиск «быстрый ноутбук для работы» с опечатками, сортировкой по релевантности и фильтрами.

Зачем синхронизация? Основные изменения происходят в PostgreSQL. Elasticsearch получает денормализованные документы для быстрого поиска; обновления могут доставляться с задержкой, которую нужно контролировать.

Production-нюанс: Двухфазной транзакции между PostgreSQL и Elasticsearch у нас по умолчанию нет. Будем отдельно изучать outbox, идемпотентность, retries и eventual consistency в M08.

Как выбирать технологию

ЗадачаОбычно PostgreSQLОбычно Elasticsearch
ACID-покупка, перевод денег✅ Транзакции и ограничения❌ Не основной выбор
Точный поиск по ID✅ Отлично✅ Возможно, но не всегда нужно

Морфология, fuzzy, синонимы, facets⚠️ Зависит от требований✅ Часто удобнее
Сложные JOIN, нормализованные отношения✅ Сильная сторона⚠️ Обычно денормализация
Логи и аналитика по времени✅ Возможно✅ Data streams и агрегации

Неочевидный момент: PostgreSQL уже умеет full-text search, индексы GIN и триграммы. Не добавляй Elasticsearch «потому что модно». Добавляй его, когда требования реально оправдывают дополнительную инфраструктуру.

Понимание под капотом

Inverted index на игрушечном примере

В обычной таблице мы идём от документа к словам. В инвертированном индексе (inverted index) — от слова к списку документов, где оно встречается.

Документы
#1 Red running shoes
#2 Blue running shirt
#3 Red winter jacket
Термин → документы
red → [1,3]
running → [1,2]
jacket → [3]
Text
→
Analyzer
→
Tokens
→
Inverted index

Это намеренно упрощённая модель. Реальный Lucene хранит дополнительные структуры — например, частоты терминов, позиции, смещения — и использует их при поиске и ранжировании.

Важно: keyword хранит значение как единый термин для точных условий, а text обычно анализирует текст в термины. Конкретное поведение зависит от mapping и analyzer — это центральная тема M03–M04.

Попробуй поиск своими руками

Ниже — учебный симулятор, не реальный Elasticsearch. Он разбивает слова, приводит их к нижнему регистру и показывает пересечение. Цель — понять инвертированный индекс, а не заменить реальное ранжирование BM25.

Здесь действует AND между словами, точное совпадение токенов и нет stemming/synonyms/fuzziness. В реальном Elasticsearch операторы и анализ задаются запросом и mapping.

REST API

Минимальный код, который понадобится в лаборатории

В следующем модуле будем выполнять эти запросы в Kibana Dev Tools или через HTTP клиент. Пока прочитай их и попробуй объяснить каждый атрибут.

Создание индекса
PUT academy-products-v1
{
  "mappings": {
    "properties": {
      "title": { "type": "text" },
      "sku": { "type": "keyword" },
      "price": { "type": "double" },
      "inStock": { "type": "boolean" }
    }
  }
}
Запись документа
PUT academy-products-v1/_doc/p-001
{
  "title": "Red running shoes",
  "sku": "SKU-001",
  "price": 79.90,
  "inStock": true
}
Полнотекстовый поиск
GET academy-products-v1/_search
{
  "query": {
    "match": { "title": "running shoes" }
  }
}
Точный фильтр
GET academy-products-v1/_search
{
  "query": {
    "term": { "sku": "SKU-001" }
  }
}
Никогда не вставляй этот учебный dev-конфиг в production. Учебная среда и production требуют разных мер защиты, TLS, секретов и ролей. Официальное предупреждение Elastic.
